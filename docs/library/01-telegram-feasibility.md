# Telegram feasibility

Assessment date 2026-11-22. This matrix describes the public protocol contracts. The disposable-channel results are pending. No sandbox channel or authorized sandbox identity was available for live validation in this change.

| Capability | Bot API administrator | MTProto | Decision for RHEA |
| --- | --- | --- | --- |
| Existing history | The HTTP API has no history enumeration endpoint. Fetching updates or copying known IDs is insufficient to inventory a channel. | [`messages.getHistory`](https://core.telegram.org/method/messages.getHistory) requires a user session and membership. [Channel updates](https://core.telegram.org/api/updates) explain gaps and old inaccessible messages. | Use paginated, bounded read-only MTProto for backfill once validated. Mark partial snapshots explicitly. |
| New posts and edits | [Webhook updates](https://core.telegram.org/bots/api#update) include `channel_post` and `edited_channel_post`. Telegram keeps pending updates up to 24 hours. Ordinary channel deletions have no equivalent Bot API update. | Channel update sequencing and `updates.getChannelDifference` support recovery, with gaps requiring reconciliation. | Bot ingestion can be optional. Reconcile with history before publishing or cleanup. |
| Copying and same-channel append | [`copyMessages`](https://core.telegram.org/bots/api#copymessages) supports known source IDs and preserves album grouping. IDs must increase within each 1–100 item request. Unavailable items can be skipped. The contract accepts source and destination chat IDs. Same-channel and old-ID behavior need live trials. | [`messages.forwardMessages`](https://core.telegram.org/method/messages.forwardMessages) accepts per-message `random_id` and optional `drop_author`. Same-channel support, exact ordering and grouping must be qualified. | Serialize target-order batches and verify the resulting stream independently. Prefer a fresh private destination in trials. |
| Reuse media | Server-side copy and, where supported, bot-scoped `file_id` reuse avoid downloading media. `file_unique_id` is an identity hint and cannot resend or prove byte equality. | [Existing media references](https://core.telegram.org/api/files) can be reused while permitted. Refresh expired file references through the original message. [`sendMultiMedia`](https://core.telegram.org/method/messages.sendMultiMedia) creates a new album subject to media-type constraints. | Preserve group membership and internal order. Avoid re-upload as a fallback for restricted content. |
| Caption vs. filename | [`editMessageCaption`](https://core.telegram.org/bots/api#editmessagecaption) edits a caption given applicable rights. A document's `file_name` is separate. | Caption edits use [`messages.editMessage`](https://core.telegram.org/method/messages.editMessage). A filename is a document attribute. | Catalog display labels and aliases are local. No rename or upload of media. |
| Deleting old posts | [`deleteMessage`](https://core.telegram.org/bots/api#deletemessage) documents a less-than-48-hour limit and permission/service-message constraints. [`deleteMessages`](https://core.telegram.org/bots/api#deletemessages) inherits those limits and may skip missing IDs. | [`channels.deleteMessages`](https://core.telegram.org/method/channels.deleteMessages) is a channel-specific call for users and bots, with admin and undeletable-message errors. Its published contract lists no equivalent age limit. Actual age and rights behavior remain unverified. | Bot API cannot be the cleanup design for K or S. A separate live qualification and approval would be needed for any MTProto cleanup. |
| IDs, dates, engagement | A copy returns new message IDs. | A new publication has new IDs and publication dates. Forward attribution varies by method and source. | Keep old-to-new IDs. Group IDs, discussion links, replies, views, reactions, pins and provenance may change or be lost. A deleted original URL cannot be repaired by recreating its media. [Private message links](https://core.telegram.org/api/links#message-links) require chat access. |
| Protected content | Forward explicitly prohibits protected content. Copy's published contract does not establish authorization to circumvent protection. | Forward may return `CHAT_FORWARDS_RESTRICTED`. | Skip and report protected or unsupported items for every transport. Treat unknown protection as a physical planning blocker until inspected. |
| Rate and cost | Follow `retry_after` for HTTP 429. [Bot FAQ](https://core.telegram.org/bots/faq#broadcasting-to-users) gives conservative chat pacing and optional paid broadcasts. | Respect [`FLOOD_WAIT_X`](https://core.telegram.org/api/errors) and persist the earliest eligible resume time. No fixed safe per-channel MTProto rate is documented. | No paid broadcasting. Quote request counts separately from time, variable hosting usage and any applicable destination charges. |
| Session and revocation | Keep the token in a separate service and rotate through BotFather. Remove channel rights on disconnect. Authenticate webhooks with Telegram's secret-token header. | A session key grants account access. Use a dedicated restricted participant wherever practical, isolated storage, and terminate the session in Telegram Devices. | Prefer read-only membership for the scan identity. Keep it outside Pages, public MCP, browser storage, and logs. |
| Licensing | Private channel administration does not grant the rights to redistribute its content. | [API terms](https://core.telegram.org/api/terms) and [content licensing](https://telegram.org/tos/content-licensing) also govern data use. [GramJS](https://github.com/gram-js/gramjs) is archived. [teleproto](https://docs.teleproto.dev/) is its maintained compatible fork and a candidate for a small isolated Node adapter. | Use synthetic original files for tests. Qualify the adapter and its dependencies before pinning a version. Keep Telegram data out of model contexts. |

**Recommendation.** Use an isolated MTProto reader for the initial backfill, an optional Bot API companion with minimal permissions, and a separate qualified copy adapter. Trial a full physical reconstruction in a new private channel with the originals preserved. If keeping the same chat is mandatory, preview the minimum contiguous suffix and consider cleanup only after both the replacement and an independently accessible, media-complete backup have been checked.
